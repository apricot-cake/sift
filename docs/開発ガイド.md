# 開発ガイド

この文書は、開発環境の準備、拡張機能の配備、実機確認を扱います。サービスごとの対象画面と実装上の制約は [対応サービス.md](対応サービス.md) を参照してください。

開発用プロファイルと日常用プロファイルは、どちらも `.output\chrome-mv3` を展開済み拡張機能として読みます。ここに置くのは WXT の production ビルドだけです。

## 開発と配備

一連の変更が完了したら、main の主作業ツリーで次のコマンドを実行します。

```powershell
npm run deploy
```

このコマンドはWXTのローカル配備用productionビルドを `.output\chrome-mv3` へ直接作成し、manifest、権限、ロケール、content script、自己リロード処理を自動検査します。検査後に `.output\native-host` へ自己リロード専用の [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) Hostを作成し、Chromeが読むHKCUへ登録して、配備IDを発行します。Hostと配備IDをリポジトリ内に置くため、日常用Chromeと配備コマンドは同じファイルを読みます。

HKCUへの登録は、Chromeと同じWindowsユーザー領域から実行する必要があります。ユーザー領域から隔離された実行では、コマンドはビルド前に失敗します。エージェントから実行する場合は、`npm run deploy` 全体にユーザー領域への書き込みを許可してください。

Siftのサイドパネルを開いている場合は新しいIDを受け取り、[`chrome.runtime.reload()`](https://developer.chrome.com/docs/extensions/reference/api/runtime/#method-reload) で同じ出力を直ちに読み直します。閉じている場合は、次に開くサイドパネルが配備済みのファイルを直接読むため、追加のリロードは行いません。Hostはサイドパネルを開いている間だけ動作します。

この仕組みを導入する最初の配備だけは、実行中の旧ビルドにサイドパネル開始時の確認処理がありません。`npm run deploy` の完了後、日常用プロファイルのSiftを一度だけ手動で再読み込みします。以後の配備は、開発用と日常用の各プロファイルでSiftを次に開いたときに反映されます。

配備前に別の出力を開発用プロファイルで確認する工程はありません。実機確認が必要な場合は、配備後に同じビルドを開発用プロファイルへ読み込みます。

## 開発用プロファイル

```powershell
npm run dev:browser
```

専用の `--user-data-dir` で Chrome を開きます。通常利用する Chrome とは別プロセスで、X などのログイン状態を独立して保持します。CDP の [`Extensions.loadUnpacked`](https://chromedevtools.github.io/devtools-protocol/tot/Extensions/#method-loadUnpacked) で `.output\chrome-mv3` を読み込み、拡張機能 ID、読込先、有効状態を確認します。初回の手動読込や、`chrome://extensions` の再読み込み操作は要りません。

開発用 Chrome は `http://127.0.0.1:9222` で CDP 接続を受け付けます。通常利用するプロファイルや、そのプロファイルに入れた操作用拡張機能は実機確認に使いません。接続に失敗した場合は開発用 Chrome を閉じ、同じコマンドで起動し直します。

開発用 Chrome は、背面や他のウィンドウに隠れた状態でも検証対象の描画とタイマーを維持します。画面の表示状態によって実機確認の結果が変わらないようにするためです。

パスと CDP 接続先だけを確認する場合は、次のコマンドを実行します。ブラウザは起動しません。

```powershell
node scripts/dev-browser.ts --print
```

実機確認では、ページへダミー投稿や検証用の DOM を追加しません。各プラットフォームが実際に読み込んだ投稿だけを使います。テスト用 HTML を使う自動検査は実機確認の代わりにしません。

自動読み込みに関わる確認は短時間で打ち切ります。読み込みが連鎖した場合は直ちにフィルターをオフにし、無限読み込みの状態を放置しません。利用者へ確認を戻す前にもフィルターがオフであることを確認します。

## Node.js

Node.js 24.12 以降が必要です。`.node-version` と `package.json` の `engines` に必要なバージョンを記載しています。CI は `.node-version` のバージョンを使います。

`scripts/` の TypeScript はビルドせずに Node.js で実行します。Node.js 24.12 で TypeScript の型除去が安定したため、このバージョンを最低要件にしています。

## 依存関係

`package.json` の依存関係はすべて完全なバージョンで固定しています。`.npmrc` の `save-exact=true` により、`npm install` が範囲指定へ書き換えることはありません。更新は Dependabot のプルリクエストで受け取ります。ワークフローの `uses:` もコミット SHA で固定しています。

### 秘密情報検査

秘密情報は GitHub Actions で検査します。Gitleaks は CI 内でのみ実行し、開発 PC には導入しません。GitHub Actions は pull request と `main` への push を検査し、秘密情報を検出した場合は失敗します。

`.gitleaksignore` は、過去の `wxt.config.js` に含まれる Chrome manifest の公開鍵だけを fingerprint で除外します。秘密鍵や認証情報ではありません。パス全体や検出ルールは除外しないため、新しい検出結果は個別に確認します。

## 文言

利用者に表示する文言は `locales/<言語>.yml` にあります。`@wxt-dev/i18n` はビルド時に各ファイルから `_locales/<言語>/messages.json` を生成します。対象言語は `en` と `ja` です。既定ロケールは `en` です。対応していない言語のブラウザには英語を表示します。

文言は次の 3 つの経路で使用します。

- コードでは `t("name")` を使います。`utils/i18n.ts` は `#i18n` の `i18n.t` を公開します。メッセージ名は `locales/en.yml` から型を生成するため、存在しない名前はコンパイルできません。複数形を持つメッセージは `t("name", 件数)` の形で呼びます。
- React で組み立てる画面では `t()` を使います。静的な文書で `data-i18n`、`data-i18n-placeholder`、`data-i18n-aria-label` を使う場合は、`localizeDocument()` が文言を置き換えます。
- `wxt.config.ts` の manifest では `__MSG_name__` を使います。これは manifest の対応フィールドだけで展開されます。

静的 HTML には、起動前にも読めるように英語の既定文言を書きます。`utils/i18n.test.ts` は、この文言が `locales/en.yml` と一致することを検証します。manifest の説明文は `verify-manifest.ts` が検証します。

`locales/locales.test.ts` は、日本語と英語が同じキーと差し込み数を持つことを検証します。複数形の表現自体は言語ごとに異なるため、比較しません。テストでは `test/i18n.ts` を通じて `locales/en.yml` を読み込み、`browser.i18n.getMessage` の代わりに使います。

## Lint

```powershell
npm run lint
```

Biome はリポジトリ全体の整形、lint、import の順序を検証します。自動修正する場合は次のコマンドを実行します。

```powershell
npm run lint:fix
```

インデント、改行、末尾改行は `.editorconfig` で定義します。Biome を使わないエディタも同じ設定を参照できます。`biome.jsonc` には `.editorconfig` で定義できない設定と、`entrypoints/content/style.css` の `!important` に関する例外だけを置いています。

## ビルドとテスト

次のコマンドはストア提出用のproductionビルドを `.output\store\chrome-mv3` に作成し、自動検査まで実行します。提出用ビルドには `nativeMessaging` 権限、Native Host名、自己リロード処理を含めません。ローカル配備用の `.output\chrome-mv3` は変更しません。

```powershell
npm run build
```

ストアへ提出するZIPも同じ条件で作成します。

```powershell
npm run zip:store
```

型検査と単体テストは、次のコマンドで実行します。

```powershell
npm test
```

このコマンドは `tsc --noEmit` の後に Vitest を実行します。テストは対象コードの隣に置きます。アダプターのテストは実際の DOM にセレクタを適用して検証します。型検査だけを実行するコマンドはありません。CI も同じコマンドを使います。
