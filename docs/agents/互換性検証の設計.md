# 互換性検証の設計

Sift が依存するサイトの構造と、実際のフィルター動作を検証する。ビルド、自動テスト、開発用 Chrome での検証を経て、合格した成果物を日常版へ配備する。検証中は日常版の成果物を上書きしない。

## 検証の構成

CI では保存済みの HTML を使い、情報の取得、ページの判定、絞り込みを検証する。

実サイトでは、並び順、投稿カード、指標、投稿日など、Sift が依存する要素の構造を保存済みの基準と比較する。投稿本文、指標の値、投稿 ID、広告は比較基準に含めない。基準の登録と更新は明示的に行い、通常の検証では上書きしない。

実サイトの E2E テストでは、閉じたパネルを起動し、実投稿を使って各フィルターの適用と解除を確認する。固定 URL だけでなく、サイト内リンクによる遷移先も検証する。期待するページ、並び順、操作欄は、Sift 自身の判定結果から生成しない。接続とアクセス権も別に検証する。

検証の定期実行は設けない。未確認、環境不備、構造差分がある結果を、自動的に合格へ変更しない。

## 合否の判定

### フィルターの操作と効果

各ページで、フィルターを適用・解除できることを確認する。条件に合う投稿を誤って隠さないことも確認する。

除外対象の投稿がない場合は「操作確認のみ」と記録し、効果確認済みには数えない。除外効果は、サイトとフィルターの組み合わせごとに、少なくとも1つの代表ページで実投稿を使って確認する。別サイトの成功では代用しない。

操作や解除を未確認のページが残っている場合は配備しない。代表ページで効果を確認できていないフィルターが残っている場合も同様とする。

### 構造差分と情報取得の失敗

構造に差分があっても動作する場合は「要確認」とする。必要な情報を取得できない場合や、操作に失敗する場合は「不合格」とする。ログイン切れや通信失敗は「検証未完了」として区別する。

実行時の状態は、対象外、読み込み中、投稿なし、アクセス権なし、必要情報の取得失敗に分ける。一部の投稿だけで情報が欠損している場合も、診断に記録する。

読み込み直後に取得失敗と断定せず、猶予時間内に復旧するか確認する。投稿がないという判定には、サイト自身の「投稿なし」表示を使う。投稿カードを取得できなかっただけでは、投稿数を0件とみなさない。構造の変更を検知しただけでは、原因がサイトの変更なのか、通信や読み込みの異常なのかは断定しない。

## フィルター単体以外の検証

次の検証はフィルター単体とは別のケースとして記録し、配備条件に含める。

### ページ遷移とパネルの再起動

対応ページから対象外ページへ移動したときに、フィルターが解除されることを確認する。対応ページへ戻ったときは、フィルターが復旧することを確認する。パネルの再起動時には、最低値が初期化されることを確認する。

### 投稿がない検索結果

`empty-x-search` では、サイトの「検索結果なし」表示を確認する。そのうえで、パネルに「投稿なし」と表示され、操作欄がなく、非表示状態も残っていないことを検証する。この結果を、通常の投稿一覧でのフィルター検証の代わりにはしない。

### プロフィールのタブ

X のプロフィールではポストを対応ケースとし、返信・動画・画像を対象外ケースとして検証する。Bluesky では投稿・メディア・ビデオを対応ケースとし、返信を対象外ケースとして検証する。

サイト内のタブやメニューで表示を切り替える。選択状態を確認してから、パネルの案内と照合する。

### 対象外のページと並び順

`unsupported-*` では、対象外のページや並び順で、閉じたパネルを起動する。対象外の案内が表示され、操作欄がないことを確認する。フィルターが無効で、非表示状態も残っていないことを確認する。

YouTube の「古い順」は、プルダウン型とチップ型を別のケースとして検証する。並び順に加え、表示形式自体も照合する。

### 検証範囲とケースの追加

代表ページに現れない A/B テストや、未知の URL 変更を網羅することはできない。異常を発見した表示形式は、個人情報を除いたテスト用データ（fixture）と検証ケースに追加する。

実行対象は `e2e/cases.ts`、通常ページのフィルター項目は `requiredFilterEvidence` で管理する。手順書の21状態・85ケースに、YouTube の表示形式、除外効果の代表ページ、投稿なし、対象外、ページ遷移のケースを追加している。

起動ケース数とフィルター項目数は別々に集計する。部分実行の成功を全検証の成功として扱わない。

## 検証結果と成果物の照合

検証結果には、ビルド ID、成果物のハッシュ、検証対象、実測結果、基準との差分を記録する。配備できるのは、検証済みの成果物と一致するものだけとする。検証後に再ビルドした場合は、別の成果物として再検証する。

ビルド ID は、実際に開いたパネルから稼働中のバックグラウンドへ問い合わせ、記録と照合する。拡張機能のファイルを再取得しただけでは、古いコードが動いていないことを確認できないため、稼働確認の代用にはしない。ビルド ID を返す応答は、ローカル配備ビルドのサイドパネルからの要求に限定する。

## 検証から配備までの実行手順

### 検証用ビルドの準備

`npm run build:candidate` で検証用の成果物を作る。各検証コマンドは起動時に候補を自動で読み込む。候補の読み込みだけを確認する場合は、`npm run browser:candidate` を使える。日常版の共有出力は変更しない。

手動確認用の開発用 Chrome が開いている場合は、読み込みや検証の前に閉じる。`browser:candidate` と各検証コマンドは、同じ開発プロファイルを CDP ポート有効で起動し、終了処理で Chrome を閉じる。ログインの準備や検証後の手動確認には `npm run browser:open` を使い、TCP 待受なしで開いて候補を読み込む。手動起動では内部の pipe 接続を保持し、Chrome のウィンドウを閉じると保持プロセスも終了する。

### 部分的な再確認と基準の更新

一部のケースを再確認するときは、`npm run test:live -- --grep <ケース名>` を使う。

基準の初回登録や更新は、`npm run test:live -- --update-snapshots` で明示的に実行し、差分を確認する。通常の実行では、基準が存在しない場合も不合格になる。基準を更新した後は、検証用の成果物をビルドし直し、通常の比較を通す。

### 全検証と合格記録

変更箇所、既知の失敗ケース、基準差分、除外効果の代表ケースを部分検証で確認してから、最終候補の全検証へ進む。失敗後は原因の切り分けと部分的な再確認を済ませてから再実行する。実行順序と結果の報告は [検証の実行順序](実機検証.md#検証の実行順序) に従う。

全検証は `npm run verify:candidate` で実行する。自動テスト、実サイトの E2E テスト、アクセス権喪失と再接続の検証がすべて成功した場合だけ、合格記録を発行する。

全検証では1つの開発用 Chrome を共有し、CDP ポートは検証コマンドの実行中だけ有効にする。子コマンドはそのセッションを再利用し、全検証の終了処理で Chrome を閉じる。プロセスを強制終了して終了処理が実行されなかった場合は、残った開発用 Chrome を閉じる。

静的検証が通った後は、実サイトの E2E テストが失敗しても接続確認まで実行する。E2E テストと接続確認のどちらかが失敗した場合は不合格とする。事前確認に不一致がある場合や、結果の照合に失敗した場合も同様とする。不合格時は終了時刻と理由を残し、合格記録は発行しない。

### 検証済み成果物の配備

`npm run deploy:local` は、ソースと成果物のハッシュを合格記録と照合する。照合後は再ビルドせず、検証済みの成果物と同じバイト列を共有出力へコピーする。旧成果物は `.output/promote-*/previous` に退避する。

## 関連する仕様と手順

操作対象は役割やラベルを優先して指定し、ユーザーに見える動作を検証する。この方針は [Playwright の Best Practices](https://playwright.dev/docs/best-practices) に沿う。構造の比較は、動作検証を補う証拠として使う。

実機での操作範囲と合否基準は [実機検証](実機検証.md) を参照する。
