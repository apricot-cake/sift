# 互換性検証の設計

sift が依存するサイトの構造と、実際のフィルター動作を検証する。検証用の成果物は日常版とは別の出力先に作る。

## 検証の構成

CI では保存済みの HTML を使い、情報の取得、ページの判定、絞り込みを検証する。

実サイトでは、選択タブ、投稿カード、指標など、sift が依存する要素の構造を保存済みの基準と比較する。投稿本文、指標の値、投稿 ID、広告は比較基準に含めない。基準の登録と更新は明示的に行い、通常の検証では上書きしない。

Bluesky の専用フィードでは、`customFeedScreen` 直下の任意の更新通知 `loadLatestBtn` だけを比較用の構造から除く。実 DOM は変更しない。その他の直下要素、画面の識別子、投稿カード、指標、URL の比較は維持する。同じ形の要素の反復数は、通知を除いた後も正規化する。

実サイトの E2E テストでは、閉じたパネルを起動し、実投稿を使って各フィルターの適用と解除を確認する。固定 URL だけでなく、サイト内リンクによる遷移先も検証する。期待するページ、並び順、操作欄は、sift 自身の判定結果から生成しない。接続とアクセス権も別に検証する。

同じ開始 URL のケースはページを共用できる。共用前にフィルターの解除と非表示状態の復元を確認し、次のケースに必要なサイトのタブ・並び順へ戻す。ケース ID、構造の比較、適用・解除・誤除外の証拠は個別に残す。仮想化された一覧は確認時点の実投稿から期待値を取り直す。復元できない場合は続行せず、失敗として記録する。

通常の実行ではキャッシュを使い、自動起動で前回のタブを復元しない。キャッシュを使わない読み込み、再読み込み、初回権限取得の代表ケースは残す。実サイトの項目を fixture の確認だけで置き換えない。

文書の読み込みと既知ホストへの fetch・XHR に検証用の予算を設け、サイト別の通信と停止理由を記録する。fetch・XHR は投稿一覧だけの件数ではなく、別ホストやサイトの worker が行う通信も網羅しない。DOM の読み取りとChrome の設定保存制限は別に扱う。予算は検証の暴走を止める上限であり、サイトから制限されない安全値とはみなさない。429、利用制限の案内、認証要求を検出したらそのサイトへのアクセスを止め、残るケースを未完了として記録する。

検証の定期実行は設けない。未確認、環境不備、構造差分がある結果を、自動的に合格へ変更しない。

## 合否の判定

### フィルターの操作と効果

各ページで、フィルターを適用・解除できることを確認する。条件に合う投稿を誤って隠さないことも確認する。

除外対象の投稿がない場合は「操作確認のみ」と記録し、効果確認済みには数えない。除外効果は、サイトとフィルターの組み合わせごとに、少なくとも1つの代表ページで実投稿を使って確認する。別サイトの成功では代用しない。

### 構造差分と情報取得の失敗

構造に差分があっても動作する場合は「要確認」とする。必要な情報を取得できない場合や、操作に失敗する場合は「不合格」とする。ログイン切れや通信失敗は「検証未完了」として区別する。

実行時の状態は、対象外、読み込み中、投稿なし、アクセス権なし、必要情報の取得失敗に分ける。一部の投稿だけで情報が欠損している場合も、診断に記録する。

読み込み直後に取得失敗と断定せず、猶予時間内に復旧するか確認する。投稿がないという判定には、サイト自身の「投稿なし」表示を使う。投稿カードを取得できなかっただけでは、投稿数を0件とみなさない。構造の変更を検知しただけでは、原因がサイトの変更なのか、通信や読み込みの異常なのかは断定しない。

## フィルター単体以外の検証

次の検証はフィルター単体とは別のケースとして記録する。

### ページ遷移とパネルの再起動

元の一覧を離れたときにパネルが閉じ、フィルターが解除されることを確認する。同じ URL の一覧タブや並び順の変更も対象とする。元の一覧へ戻ってもパネルとフィルターは復旧しない。同じ一覧の再読み込みと、元の一覧を背景に持つライトボックスでは維持する。パネルの再起動時には、最低いいね数が「指定なし」に戻ることを確認する。

パネルはブラウザのタブごとに検証する。A で開いたパネルは未開封の B へ引き継がれず、A へ戻ると再表示されることを確認する。B でも明示的に開いた後は、タブを往復しても各パネルの所有タブ ID と操作欄が保たれることを確認する。同じタブ内の移動、再読み込み、別サイトへの移動による閉鎖と再接続は、タブ切り替えとは別に確認する。

起動時は拡張アクションで `activeTab` の一時的なアクセス権を取得し、タブ別のパネルを開く。タブ切り替え時の非表示・復元は Chrome が管理する。閉じた後もパネルの設定は有効なままであり、`getOptions().enabled` だけでは開閉を判定しない。可視状態、開閉通知、ページ幅を照合する。

### 投稿がない検索結果

`empty-x-search` では、サイトの「検索結果なし」表示を確認する。そのうえで、パネルに「投稿なし」と表示され、操作欄がなく、非表示状態も残っていないことを検証する。この結果を、通常の投稿一覧でのフィルター検証の代わりにはしない。

### 画像のライトボックス

`lightbox-x` では、対応するプロフィール一覧から実投稿の画像を開く。画像・動画のみの条件、元一覧の識別子と集計が保持され、ライトボックス内の投稿が除外されないことを確認する。Escape で閉じた後も同じ設定と集計に戻ることを確認する。画像詳細 URL への直接アクセスは、元一覧を持たない対象外ページとして確認する。

### プロフィールのタブ

X のプロフィールではポストを対応ケースとし、返信・動画・画像を対象外ケースとして検証する。Bluesky では投稿・メディア・ビデオを対応ケースとし、返信を対象外ケースとして検証する。

サイト内のタブやメニューで表示を切り替える。選択状態を確認してから、パネルの案内と照合する。

### 対象外のページと並び順

`unsupported-*` では、対象外のページや並び順で、閉じたパネルを起動する。対象外の案内が表示され、操作欄がないことを確認する。フィルターが無効で、非表示状態も残っていないことを確認する。

### 検証範囲とケースの追加

代表ページに現れない A/B テストや、未知の URL 変更を網羅することはできない。異常を発見した表示形式は、個人情報を除いたテスト用データ（fixture）と検証ケースに追加する。

実行対象は `e2e/cases.ts`、通常ページのフィルター項目は `requiredFilterEvidence` で管理する。手順書の14状態・70ケースに、除外効果の代表ページ、投稿なし、対象外、ページ遷移のケースを追加している。

E2E の実行数は29ケースで、対応ページ16、対象外9、ページ遷移2、投稿なし1、ライトボックス1に分ける。対応ページでは X・Bluesky を確認する。起動ケースとフィルター項目の数は、手順書の表と別に集計する。

起動ケース数とフィルター項目数は別々に集計する。部分実行の成功を全検証の成功として扱わない。

## 検証結果と成果物の照合

検証結果には、ビルド ID、成果物のハッシュ、検証対象、実測結果、基準との差分を記録する。再ビルドした成果物は、以前の検証結果と区別する。

拡張機能のソースハッシュには、未追跡の実装やテストも含める。

ビルド ID は、実際に開いたパネルから稼働中のバックグラウンドへ問い合わせ、記録と照合する。拡張機能のファイルを再取得しただけでは、古いコードが動いていないことを確認できないため、稼働確認の代用にはしない。ビルド ID を返す応答は、ローカル配備ビルドのサイドパネルからの要求に限定する。

## 検証と配備の実行手順

### 検証用ビルドの準備

`pnpm run build:candidate` で検証用の成果物を作る。各検証コマンドは起動時に候補を自動で読み込む。候補の読み込みだけを確認する場合は、`pnpm run browser:candidate` を使える。日常版の共有出力は変更しない。

手動確認用の開発用 Chrome が開いている場合は、読み込みや検証の前に閉じる。`browser:candidate` と各検証コマンドは、Puppeteer で同じ開発プロファイルを pipe 接続で起動し、終了処理で Chrome を閉じる。

候補は `Browser.installExtension()` で読み込み、読み込み前の worker を除外して、実行中のバックグラウンドのビルド ID を照合する。旧ビルドが動いている場合だけ `chrome.runtime.reload()` を実行し、別の worker の起動を待ってビルド ID を再照合する。成果物のハッシュは読み込み前後に確認する。

ログインの準備や検証後の手動確認には `pnpm run browser:open` を使う。手動起動では保持プロセスが pipe 接続を維持し、Chrome のウィンドウを閉じると保持プロセスも終了する。自動・手動のどちらも TCP の CDP ポートは開かない。

### 部分的な再確認と基準の更新

一部のケースを再確認するときは、`pnpm run test:live --testNamePattern <ケース名>` を使う。

基準の初回登録や更新は、`pnpm run test:live --update` で明示的に実行し、差分を確認する。通常の実行では、基準が存在しない場合も不合格になる。基準を更新した後は、検証用の成果物をビルドし直し、通常の比較を通す。

### 全検証と合格記録

変更箇所、既知の失敗ケース、基準差分、除外効果の代表ケースを部分検証で確認してから、最終候補の全検証へ進む。失敗後は原因の切り分けと部分的な再確認を済ませてから再実行する。実行順序と結果の報告は [検証の実行順序](実機検証.md#検証の実行順序) に従う。

全検証は `pnpm run verify:candidate` で実行する。自動テスト、実サイトの E2E テスト、アクセス権喪失と再接続の検証がすべて成功した場合だけ、合格記録を発行する。

全検証は各コマンドを順番に実行する。Chrome を使うコマンドは、自分が起動した Chrome の pipe 接続を保持し、終了処理で Chrome を閉じる。実サイトの E2E テストは1回の起動で全ケースを順番に検証し、ファイルをまたぐ同じ開始URLのページも共用する。いずれも同じ開発プロファイルを使い、ログイン状態を引き継ぐ。プロセスを強制終了して終了処理が実行されなかった場合は、残った開発用 Chrome を閉じる。

静的検証が通った後は、通常の E2E 失敗でも接続確認まで実行する。ただし、サイトの利用制限を検出した場合は、そのサイトへアクセスする接続確認も止める。E2E テストと接続確認のどちらかが失敗・未完了の場合は合格記録を発行しない。事前確認に不一致がある場合や、結果の照合に失敗した場合も同様とする。終了時刻、失敗と未完了の区別、停止理由を残す。

### 日常版への配備

main の主作業ツリーで `pnpm run deploy:local` を実行する。現在のソースをビルドして共有出力へ配備する。旧成果物は `.output/promote-*/previous` に退避する。

## 関連する仕様と手順

操作対象は役割やラベルを優先して指定し、ユーザーに見える動作を検証する。[Puppeteer のページ操作](https://pptr.dev/guides/page-interactions)に従い、Locator と ARIA セレクターを使う。構造の比較は、動作検証を補う証拠として使う。

実機での操作範囲と合否基準は [実機検証](実機検証.md) を参照する。
