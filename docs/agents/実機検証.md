# 実機検証

sift の対応ページで、パネルの起動、フィルターの適用と解除、ページ遷移を検証する。検証を依頼するときは「実機検証手順に沿ってスモークテストして」と指定する。

## 検証の準備

1. `pnpm run typecheck` と `pnpm test` を実行する。必要に応じて `pnpm run lint` も実行する。これらの結果は実機検証の結果と分けて記録する。
2. 拡張機能を変更した場合は、`pnpm run build:candidate` で検証用の成果物を作り、ビルド ID と成果物のハッシュを記録する。各検証コマンドは起動時に候補を自動で読み込む。候補の読み込みだけを確認する場合は `pnpm run browser:candidate` を使える。
3. ログインなどの準備は `pnpm run browser:open` で開発プロファイルを開いて行い、準備後にその Chrome を閉じる。自動検証コマンドは Puppeteer で同じプロファイルの Chrome を pipe 接続で起動し、終了処理で閉じる。自動検証には現行 Chrome の Headless モードを使い、ウィンドウを表示しない。スクロールバーは通常表示と同じ条件にする。日常用の Chrome は使わない。
4. 終了後に設定を復元できるよう、`chrome.storage.sync` の `settings` をローカルの `test-results/` などへ退避する。Cookie や認証情報は取得・記録しない。
5. 自動検証では前回のタブを復元せず、検証用に作成したページを再利用する。Cookie と通常のキャッシュは保持する。同じ開始 URL のケースでも、設定の解除とサイトの選択状態を確認してから共用する。終了時は作成したページを閉じる。

`smoke:panel`、`smoke:connection`、`browser:candidate` は、それぞれ自分が起動した Chrome を pipe 接続で操作し、終了処理で閉じる。`test:live` は1回の起動で全ケースを順番に検証し、全体の終了処理で Chrome を閉じる。`verify:candidate` は検証コマンドを順番に実行する。各起動で同じ開発プロファイルを使うため、ログイン状態は引き継がれる。`pnpm run browser:status` はプロファイルと pipe 接続の設定を表示し、Chrome の起動状況は取得しない。自動検証後の手動確認には `pnpm run browser:open` を使う。手動起動では保持プロセスが pipe 接続を維持し、Chrome のウィンドウを閉じると保持プロセスも終了する。どのコマンドも TCP の CDP ポートは開かない。

サイト上での投稿、いいね、フォロー、リポスト、リスト編集などは行わない。検証には読み込み済みの実投稿を使い、ダミー投稿や検証用 DOM は追加しない。スクロールや巡回は無制限に行わない。

### サイトへの負荷と制限

実サイトの検証項目は減らさず、重複するページ取得を減らす。構造の照合、フィルターの適用・解除、対象外への切り替えを同じページで行う場合も、それぞれのケースと証拠を記録する。前のケースの非表示状態や選択値が残っていないことを確認できなければ、そのページを共用しない。

通常のフィルター検証では、設定を退避してから対象サイトの条件を解除し、ページを開く。保存済みの条件によって初期一覧の大半が隠れ、サイトの追加取得が始まることを避ける。その後のUIからの適用・解除、誤除外、起動時の条件リセットは引き続き確認する。設定の退避は実行ごとに別のファイルへ保存する。設定・タブ・パネル通知は同じ拡張機能の静的ページから観測し、終了時は保存値の一致を確認する。backgroundの稼働はアクションの起動とパネルからのビルドID応答で検証する。この終了処理によってケースの失敗を合格に変えない。

最低いいね数の候補は、残る件数が全体の半数に近いものを優先する。除外効果と誤除外の確認を維持し、一覧の大半を隠す条件による追加取得を減らす。適用時は、UI操作に加えて選択した条件の保存完了を確認する。

Bluesky の追加取得に必要なレイアウト確認は、最低値や期間に一致した投稿だけでなく、種別条件で残した投稿や指標を読めず安全のため残した投稿も数える。残る投稿が画面下にある場合は、自動スクロールで追加取得を誘発しない。全投稿が除外された場合など、実際に表示を埋める必要がある場合の確認は維持する。

通常はキャッシュを使う。キャッシュを無効にした読み込み、再読み込み、権限取得からの起動は、復旧や初期状態を確認する代表ケースで残す。キャッシュを使った結果だけで、初期状態の確認を代用しない。

キャッシュ無効の代表は各サイトの最初の成功ケースとする。`DOMContentLoaded` では戻さず、対象一覧の選択・実投稿の読み込み・パネルの状態確認が完了してからキャッシュを戻す。以後のフィルター操作と共有ケースはキャッシュを使う。完了時の状態とキャッシュ無効の有無を `initialization-cache` に記録し、途中で失敗したケースは代表確認済みに数えない。

サイト別に、文書の読み込み、既知ホストへの fetch・XHR、読み込み前の待機時間、停止理由を `test-results/live-load.json` に記録する。fetch・XHR の件数には一覧以外の通信も含み、別ホストやサイトの worker が行う通信は網羅しない。全検証では E2E 終了時と接続確認終了時の通信量も別ファイルへ保存し、どの段階で上限に達したかを確認する。実測なしに負荷削減率を報告しない。追加取得と繰り返し遷移には検証用の予算を設ける。予算は無制限な巡回を止めるためのもので、BAN を防げる閾値とは扱わない。

429、サイト自身の利用制限表示、認証要求、追加の認証画面を検出した場合は、そのサイトの検証を止める。Retry-After がある場合は記録し、指示された待機時間より早く再取得しない。別のページやブラウザの再起動で制限を回避しない。停止したケースと未実行のケースは「検証未完了」とし、全検証の合格記録を発行しない。接続確認でも制限されたサイトへ新たにアクセスしない。

通信の内訳は `test-results/live-load.network.jsonl` に実行 ID、ケース、操作段階、API 操作名、ページ追加の有無、応答状態、キャッシュ利用として記録する。URL 全体、クエリ、検索語、本文、ヘッダーは保存しない。`node scripts/compatibility/network-report.ts [実行ID] --site <サイト>` で fetch・XHR を集計する。サイトは `x`、`bluesky` を指定でき、省略時は `x` とする。継続を許可したリクエストにもキャッシュ利用が含まれるため、その件数を実際のサーバー送信件数と同一視しない。同じ操作名の反復だけで重複した要求とも判定しない。

許可取得の準備用開閉は、タブとオリジンごとの初回だけ行う。別オリジンへの移動やタブ閉鎖では準備記録を破棄する。各ケースでは引き続き、閉じた状態からの実アクションによる起動、開閉通知、ページ幅、可視パネル、所有タブを確認する。

X のプロフィールからメディア、検索から検索結果なしのケースへ進むときは、既存のページでサイトのリンクや検索欄を操作する。遷移先の URL、選択したタブ、表示内容を確認し、対象ケースだけを実行した場合も同じ合否基準を使う。すでに選択済みのタブは再クリックせず、選択状態を検証する。

Bluesky でも、サイト自身の選択表示を確認できたタブは再クリックしない。対象外への切り替え、対応ページへの復帰、フィルター解除とパネル再起動の判定は省略しない。

サイト別の共用では、X は検索語をネイティブ検索欄で切り替える。Bluesky の専用リストはホームからリスト一覧へ進み、固定の専用 URL のリンクを開く。同名のホーム固定リストとは区別する。

DOM の読み取りや拡張機能への問い合わせを、サイトへの通信回数として数えない。Chrome の設定保存回数制限もサイトの利用制限とは別に扱い、設定の保存と復元に必要な余裕を残す。

通信予算は1サイトにつき文書読み込み40回・fetchとXHR400回、1ケースにつきfetchとXHR60回とする。ページを共用しても、サイト全体の予算はリセットしない。同じサイトの文書読み込みは最低2秒の間隔を空ける。これらは検証の内部上限であり、公式の許容量ではない。429の `Retry-After` を記録し、待機期限を次の実行にも引き継ぐ。期限が不明な429では最低15分間アクセスしない。

ホームのカスタムフィード検証には、開発プロファイルで Discover（日本語表示「みつけよう」）を固定しておく。検証コマンドはフィードの固定・解除を行わない。

## 検証対象とケース数

フィルターは一つずつ検証し、組み合わせは検証しない。他のフィルターを無効にしたうえで、対象フィルターの適用から解除までを1ケースとする。プルダウンでは全候補を試すのではなく、表示される投稿と非表示になる投稿の両方が生じる値を選ぶ。

| サイト | ページ | 並び順 | 単体で確認する項目 | 状態数 | ケース数 |
| --- | --- | --- | --- | ---: | ---: |
| X | フォロー中、ホーム内固定リスト、リスト専用ページ、検索、プロフィールのポスト | 検索は最新のみ。他はサイトの通常表示 | 最低いいね数、コンテンツタイプ、返信・引用投稿・リポストを除外 | 5 | 25 |
| Bluesky | フォロー中、ホーム内固定リスト・カスタムフィード、リスト・フィード専用ページ、検索、プロフィールの投稿・メディア・ビデオ | 検索は最新のみ。他はサイトの通常表示 | 最低いいね数、コンテンツタイプ、返信・引用投稿・リポストを除外 | 9 | 45 |
| 合計 | | | | 14 | 70 |

この表の14状態・70ケースは上限とする。サイトに存在しないタブや並び順は「対象なし（N/A）」と記録し、合格には数えない。対象範囲は [対応サービス](../対応サービス.md) と照合する。

自動 E2E の実行数は29ケースで、対応ページ16、対象外9、ページ遷移2、投稿なし1、ライトボックス1に分ける。ページの共用や確認のまとめ方を変えても、ケース ID と各項目の合否は維持する。表のフィルター項目数と E2E の実行数は別々に集計する。

## パネルの開閉

各ページ・並び順で、パネルを閉じた状態から起動する。開いたパネルを使い回しただけでは、起動確認を合格にしない。

```sh
pnpm run smoke:panel "https://x.com/NASA"
```

このコマンドは、指定 URL の実ページを検証用 Chrome で開く。同じ URL のタブが1つ存在する場合は再利用する。検証のために作成したタブは終了時に閉じる。Headless Chrome の起動では前回のタブの復元を前提にしない。ページ遷移やフィルター単体の検証は実行しない。

### コマンドの確認手順

1. CDP の `Extensions.triggerAction` でパネルを準備起動する。これは再起動後の `activeTab` 権限を取得するための操作であり、初回起動の合格には数えない。
2. 拡張機能のバックグラウンドに、`sidePanel.onOpened` と `onClosed` を観測する一時リスナーを登録する。サイトの DOM は変更しない。
3. パネルを閉じ、通知履歴を消去する。ページの表示幅を記録する。
4. 拡張アクションを呼び出し、対象のタブ ID、ウィンドウ ID、パスに一致する `onOpened` を待つ。パスは `sidepanel.html` と `/sidepanel.html` を同一と扱う。
5. ページ幅が縮小したことを確認する。パネルの `visibilityState === "visible"`、表示寸法、接続先タブ、内容も確認する。
6. パネルを閉じ、同じ対象の `onClosed` とページ幅の復元を確認する。
7. 一時リスナーを解除し、CDP 接続を閉じる。結果を JSON で標準出力へ出す。判定に失敗した場合は終了コード1になる。

### 設定への影響と判定の範囲

準備起動を含め、パネルの起動時には sift の通常動作によって最低値が「指定なし」に戻る。このため、実行前に設定を退避する。終了時はパネルを閉じ、設定を復元して保存内容を照合する。検証コマンドの終了処理で Chrome も閉じる。強制終了で終了処理が実行されなかった場合は、残った開発用 Chrome を閉じる。

対象タブが複数ある、バックグラウンドが見つからない、開閉通知が来ない、ページ幅が変わらない場合は、環境と結果を記録する。推測で合格にせず、幅の変化だけでも合格にしない。

この検証では、ツールバーのアイコンを実際にクリックしていない。必要な場合は、ユーザーによるクリックの結果を別に記録する。CDP ターゲットの存在、`getOptions().enabled`、パネル単体のキャプチャだけでは、パネルが実際に表示された証拠にはならない。また、開閉確認ではレイアウトの崩れまでは検証できない。

## フィルター単体の検証

開閉確認の後にパネルを開き直す。対象タブと表示内容が正しいことを確認してから、次の手順を実行する。「接続とアクセス権」の検証も毎回行う。

1. 最低値を「指定なし」、除外トグルをオフ、コンテンツタイプを制限なしにする。
2. DOM から実際のラベルと位置を読み取る。操作には CDP の `Input.dispatchMouseEvent`、`Input.dispatchKeyEvent`、`Input.insertText` を使う。設定ストレージの直接書き換えや DOM の `.click()` では、操作の検証を代用しない。
3. フィルターを1つ適用する。UI の選択値を確認し、実投稿の指標・種類と表示結果を照合する。`data-sift-filter-state` と `data-sift-filter-reason` は補助情報として使う。これらの属性だけでは期待値が正しいことを証明できない。
4. フィルターを解除し、非表示状態が残らないことを確認する。
   同じページを次の確認に使う場合は、最低値が「指定なし」、除外トグルがオフ、コンテンツタイプが制限なしであることと、サイト側のタブ・並び順を確認する。仮想化により投稿が入れ替わった場合は、実際に表示された投稿で新しい観測を取り、前の件数を引き継がない。
5. 追加読み込みで件数が変わった場合は、対象投稿と確認時点を記録して比較する。件数は固定とみなさない。連続読み込みが続く場合は条件を解除し、そのケースを中断したことを記録する。

除外対象の投稿がない場合は「操作確認のみ」と記録し、効果確認済みには数えない。指標が欠損した投稿は、仕様上、非表示にしない。

## 接続とアクセス権

接続とアクセス権は、毎回のスモークテストで確認する。表の70ケースとは別に実施し、通常の開閉確認では代用しない。パネルを閉じても `activeTab` の権限は残るため、準備起動後の開閉だけでは未許可状態を確認できない。

```sh
pnpm run smoke:connection
```

実行前に、手動確認用の開発用 Chrome を閉じる。X のプロフィールを閲覧できるよう、開発プロファイルでログインしておく。コマンドは Chrome を起動し、検証用タブを2つ作って次の状態を確認する。

| 状態 | 合格条件 |
| --- | --- |
| X のプロフィールで拡張アクションを実行する | 対象タブの最低いいね数などの操作欄が表示される |
| 同じタブで Bluesky のプロフィールへ移動する。拡張アクションは実行しない | パネルが自動で閉じ、ページ幅が開く前に戻る |
| Bluesky で拡張アクションを実行する | 同じタブに再接続し、最低いいね数などの操作欄が表示される |
| Bluesky のプロフィールで「フィード」タブへ移動する | パネルが閉じ、ページ幅が元に戻る |
| 「投稿」タブへ戻り、拡張アクションを実行する | フィルターが初期化されたパネルが開く |
| 別の X プロフィールタブで拡張アクションを実行する | 接続先が新しいタブに変わり、最低いいね数の操作欄が表示される |
| 元の Bluesky タブへ戻る | 接続先と操作欄が Bluesky に戻る |

各段階で、パネルの可視状態、表示寸法、アクティブタブ ID、サイト別の内容を照合する。セッションストレージのタブ ID は最後の起動先を示すため、現在の接続先の証拠には使わない。期待した状態を連続して確認できなければ失敗とする。ログイン画面、読み込み失敗、権限が常時付与された環境などで前提を再現できない場合も、合格にはしない。

結果は `test-results/connection-smoke.json` に保存される。失敗時は終了コード1になる。ビルド ID は準備時の記録と併せて残す。

終了時は作成したタブだけを閉じ、退避した設定を復元する。設定の退避先は `test-results/connection-settings-before.json`。強制終了した場合も、このデータから設定を復元し、作成したテスト用タブを閉じる。

この検証の対象は CDP 経由の接続状態である。ツールバーの実クリックに固有の問題や、全ページのフィルター動作までは検証できない。

## 対象外ページとページ遷移

以下の確認も、表の70ケースとは別に実施する。対象外ページで拡張アクションを実行し、案内パネルが開くことを確認する。フィルター操作欄が表示されず、ページ上に非表示状態が残らないことも確認する。

| サイト | 対象外の代表例 |
| --- | --- |
| X | おすすめ、検索の最新以外、個別投稿、プロフィールのポスト以外のタブ |
| Bluesky | 検索の最新以外、個別投稿、プロフィールの返信 |
| 対象外サイト | example.com など |

対象外サイトに処理が注入されないことは、バックグラウンド処理のテストと併せて確認する。

パネルを開いたまま元の一覧を離れると、パネルが閉じてフィルターが解除されることを確認する。同じ URL の一覧タブや並び順の変更も対象とする。元の一覧へ戻ってもパネルとフィルターが復旧しないことを確認する。同じ一覧の再読み込みと、元の一覧を背景に持つライトボックスでは維持する。パネルを開き直したときは、選択値が「指定なし」に戻ることを確認する。拡張機能の更新を挟むケースは、ビルドごとに結果を記録する。

`pnpm run smoke:connection` では、A タブで開いたパネルが未開封の B タブへ引き継がれず、B のページ幅が戻ることを確認する。A に戻ると A のパネルが再表示されること、B で拡張アクションを実行すると B 用のパネルが開くことも確認する。その後は両タブを往復し、表示中のパネルの所有タブ ID と操作欄が一致することを確認する。

## 結果の記録と終了処理

結果は Git 管理外の `test-results/` に保存する。日時、ビルド ID、Chrome のバージョン、ページ、並び順、操作方法、条件、期待値、実測結果、判定、未確認の理由を記録する。記録には次の形式を使える。

| ページ・並び順 | 起動方法と結果 | フィルター | 条件 | 期待値・実測結果 | 判定・理由 |
| --- | --- | --- | --- | --- | --- |
| | CDP アクション／実クリック | | | | 合格／不合格／操作確認のみ／N/A／未実施 |

起動を確認した状態数とフィルターのケース数は、別々に集計する。途中結果や古いビルドの結果を、全件完了として扱わない。途中で修正した場合はビルド ID を更新し、影響するケースを再検証する。

終了時は変更した設定を元に戻す。一時リスナーを解除し、CDP 接続を閉じる。作成したテスト用タブを閉じ、検証コマンドの終了処理で Chrome も閉じる。検証だけを依頼された場合は、失敗を見つけても実装を変更せず、結果を報告する。

## 検証と配備

### 検証の実行順序

検証範囲は、変更の動作・表示・権限・データ処理への影響に応じて決める。以下の実機検証と配備は、動作や画面に影響する変更を対象とする。

全検証は、変更箇所と既知の失敗を部分検証で解消した後に実行する。

1. 報告されたページで再現する。変更箇所の単体テストと、対象ページの部分検証を先に実行する。表示形式に依存する判定では、操作欄がある場合だけでなく、正常に省略される場合、読み込み途中、未知の表示を区別する。
2. 基準の登録・更新を済ませ、差分を確認する。通常の比較で対象ケースが通ることを確認する。除外効果の代表ケースでは、実際に除外対象があることも確認する。外部サイトの見出し変更など、拡張機能と無関係な検証前提の不一致も、この段階で解消する。
3. ソース、テスト、基準、文書の変更を終えて候補をビルドする。検証中はこれらを編集せず、開発用 Chrome を使う実機検証も同時に実行しない。
4. `pnpm run verify:candidate` を実行する。

全検証が失敗した場合は、結果を読んで、実装、検証の期待値、ログイン・通信・保存回数制限などの環境問題に切り分ける。失敗ケースを `pnpm run test:live --testNamePattern <ケース名>` で再確認し、必要な修正を終えてから全検証へ戻る。原因を確認しないまま全検証を繰り返さない。再実行前には、失敗の原因、修正または環境の復旧内容、部分検証の結果を説明する。

設定の保存回数制限が出た場合は、設定の退避・復元と検証用タブの後片付けを確認し、保存回数と経過時間を記録する。Chrome の制限期間が過ぎるまで待ってから再確認する。ブラウザの再起動を制限解除の証拠にはしない。サイトの利用制限が出た場合は、サイト側の案内に従い、復旧を確認するまでそのサイトの部分検証も繰り返さない。いずれも制限値や判定を緩めて合格にしない。

文書や作業指示だけの変更では、Markdown の検査と差分確認を行う。拡張機能の再ビルド、実機検証、配備は、その変更だけを理由に実行しない。

パッケージの名前・概要などのメタデータだけの変更では、内容と文字数などの仕様上の制限を確認し、必要に応じてストア提出用パッケージを生成して反映を確認する。実機検証とローカル配備は、動作や画面にも影響する場合に行う。ロケールの変更でも、拡張機能内の画面表示に使う文言と、パッケージ概要だけに使う文言を区別する。

### 合格の報告

途中のログやケース数だけで全検証の通過を報告しない。終了コード、`.output/verified-candidate.json` の `status` とビルド ID、実機レポート、接続確認の結果を照合する。全ケースが通っても、代表ページの除外効果が不足して合格記録が発行されていなければ、全検証は未完了とする。

検証記録には実行範囲、所要時間、再実行した場合の理由を残す。部分検証、全検証、配備済みの状態を分けて報告する。

### 日常版への配備

main の主作業ツリーで `pnpm run deploy:local` を実行する。このコマンドは現在のソースをビルドして配備する。詳しくは [互換性検証の設計](互換性検証の設計.md) を参照する。
