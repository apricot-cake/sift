# 実機検証

Sift の対応ページで、パネルの起動、フィルターの適用と解除、ページ遷移を検証する。検証を依頼するときは「実機検証手順に沿ってスモークテストして」と指定する。

## 検証の準備

1. `npm run typecheck` と `npm test` を実行する。必要に応じて `npm run lint` も実行する。これらの結果は実機検証の結果と分けて記録する。
2. 拡張機能を変更した場合は、`npm run build:candidate` で検証用の成果物を作り、ビルド ID と成果物のハッシュを記録する。各検証コマンドは起動時に候補を自動で読み込む。候補の読み込みだけを確認する場合は `npm run browser:candidate` を使える。日常版への配備は検証後に行う。
3. ログインなどの準備は `npm run browser:open` で開発プロファイルを開いて行い、準備後にその Chrome を閉じる。自動検証コマンドは同じプロファイルの Chrome を CDP ポート有効で起動し、終了処理で閉じる。日常用の Chrome は使わない。
4. 終了後に設定を復元できるよう、`chrome.storage.sync` の `settings` をローカルの `test-results/` などへ退避する。Cookie や認証情報は取得・記録しない。
5. 既存のタブを再利用して対象ページを開く。各サイトで再利用するタブは残し、用済みのテスト用タブだけを閉じる。

`test:live`、`smoke:panel`、`smoke:connection`、`browser:candidate` は、それぞれ実行中だけ CDP ポートを有効にする。`verify:candidate` は全検証中に同じ Chrome を共有する。CDP の TCP 接続先は実行中に `npm run browser:status` で確認できる。自動検証の終了後に手動確認する場合は、`npm run browser:open` で同じプロファイルを TCP 待受なしで開き直す。手動起動でも候補を読み込むために内部の pipe 接続を維持し、Chrome のウィンドウを閉じると保持プロセスも終了する。ログイン状態は保持される。

サイト上での投稿、いいね、フォロー、リポスト、リスト編集などは行わない。検証には読み込み済みの実投稿を使い、ダミー投稿や検証用 DOM は追加しない。スクロールや巡回は無制限に行わない。

## 検証対象とケース数

フィルターは一つずつ検証し、組み合わせは検証しない。他のフィルターを無効にしたうえで、対象フィルターの適用から解除までを1ケースとする。プルダウンでは全候補を試すのではなく、表示される投稿と非表示になる投稿の両方が生じる値を選ぶ。

| サイト | ページ | 並び順 | 単体で確認する項目 | 状態数 | ケース数 |
| --- | --- | --- | --- | ---: | ---: |
| YouTube | チャンネルの動画・配信 | 新しい順 | 最低再生回数、新しい動画を除外、メンバー限定を除外 | 2 | 6 |
| YouTube | 同上 | 人気の動画 | 投稿期間、再生回数の上限、メンバー限定を除外 | 2 | 6 |
| YouTube | チャンネルのショート | 新しい順・人気の動画 | 最低再生回数、メンバー限定を除外、人気の動画では再生回数の上限 | 2 | 5 |
| ニコニコ動画 | ユーザーの投稿動画一覧 | 投稿日時が新しい順・再生数が多い順 | 最低再生回数、新しい動画を除外、再生数が多い順では再生回数の上限 | 2 | 5 |
| X | フォロー中、ホーム内固定リスト、リスト専用ページ、検索、プロフィールのポスト | 検索は最新のみ。他はサイトの通常表示 | 最低いいね数、コンテンツタイプ、返信・引用投稿・リポストを除外 | 5 | 25 |
| Bluesky | フォロー中、ホーム内固定リスト、リスト専用ページ、検索、プロフィールの投稿・メディア・ビデオ | 検索は最新のみ。他はサイトの通常表示 | 最低いいね数、コンテンツタイプ、返信・引用投稿・リポストを除外 | 7 | 35 |
| YouTube | チャンネル内検索 | サイトの検索結果順 | 最低再生回数、新しい動画を除外、メンバー限定を除外 | 1 | 3 |
| 合計 | | | | 21 | 85 |

この表の21状態・85ケースは上限とする。サイトに存在しないタブや並び順は「対象なし（N/A）」と記録し、合格には数えない。対象範囲は [対応サービス](../対応サービス.md) と照合する。

YouTube のショート一覧には投稿日がないため、どちらの並び順でも最低再生回数で絞り込む。ニコニコ動画の「再生数が多い順」では、最低再生回数と「新しい動画を除外」を確認する。YouTube のような投稿期間の操作欄はない。

### YouTube の並び順の表示形式

動画数の少ないチャンネルでは並び順の選択欄が表示されない場合がある。この表示でも最低再生回数、新しい動画の除外、メンバー限定の除外を確認する。確認例は `https://www.youtube.com/@SAYOSAYOCh/videos`。並び順の案内は表示しない。

並び順の判定を変更した場合は、タブ・チップ型とプルダウン型の両方を検証する。それぞれで「新しい順」「人気の動画」の操作欄と、「古い順」の対象外表示を確認する。

プルダウン型の確認例は `https://www.youtube.com/@sutehage_channel/videos`。表示形式はサイト側で変わるため、検証時に実際の要素を確認し、結果に記録する。

## パネルの開閉

各ページ・並び順で、パネルを閉じた状態から起動する。開いたパネルを使い回しただけでは、起動確認を合格にしない。

```sh
npm run smoke:panel -- "https://www.youtube.com/@Google/shorts"
```

このコマンドは、指定 URL と完全に一致する既存タブ1つを対象にする。事前に `browser:open` で対象 URL のタブを1つ開き、その Chrome を閉じる。検証コマンドは起動時に前回のタブを復元する。ページ遷移やフィルター単体の検証は実行しない。実行中はウィンドウのサイズやタブを手動で変更しない。

Playwright で Chrome に接続したプロセスから呼び出す場合は、`spawn` などで非同期に実行する。`spawnSync` で待機すると、Playwright が新しいパネルへ接続する処理も止まる。その結果、開閉通知を取得できなくなる。

### コマンドの確認手順

1. CDP の `Extensions.triggerAction` でパネルを準備起動する。これは再起動後の `activeTab` 権限を取得するための操作であり、初回起動の合格には数えない。
2. 拡張機能のバックグラウンドに、`sidePanel.onOpened` と `onClosed` を観測する一時リスナーを登録する。サイトの DOM は変更しない。
3. パネルを閉じ、通知履歴を消去する。ページの表示幅を記録する。
4. 拡張アクションを呼び出し、対象のタブ ID、ウィンドウ ID、パスに一致する `onOpened` を待つ。パスは `sidepanel.html` と `/sidepanel.html` を同一と扱う。
5. ページ幅が縮小したことを確認する。パネルの `visibilityState === "visible"`、表示寸法、接続先タブ、内容も確認する。
6. パネルを閉じ、同じ対象の `onClosed` とページ幅の復元を確認する。
7. 一時リスナーを解除し、CDP 接続を閉じる。結果を JSON で標準出力へ出す。判定に失敗した場合は終了コード1になる。

### 設定への影響と判定の範囲

準備起動を含め、パネルの起動時には Sift の通常動作によって最低値と投稿期間が「指定なし」に戻る。このため、実行前に設定を退避する。終了時はパネルを閉じる。検証コマンドの終了処理で Chrome も閉じる。強制終了で終了処理が実行されなかった場合は、残った開発用 Chrome を閉じる。

対象タブが複数ある、バックグラウンドが見つからない、開閉通知が来ない、ページ幅が変わらない場合は、環境と結果を記録する。推測で合格にせず、幅の変化だけでも合格にしない。

この検証では、ツールバーのアイコンを実際にクリックしていない。必要な場合は、ユーザーによるクリックの結果を別に記録する。CDP ターゲットの存在、`getOptions().enabled`、パネル単体のキャプチャだけでは、パネルが実際に表示された証拠にはならない。また、開閉確認ではレイアウトの崩れまでは検証できない。

## フィルター単体の検証

開閉確認の後にパネルを開き直す。対象タブと表示内容が正しいことを確認してから、次の手順を実行する。「接続とアクセス権」の検証も毎回行う。

1. 最低値を「指定なし」、除外トグルをオフ、コンテンツタイプを制限なしにする。
2. DOM から実際のラベルと位置を読み取る。操作には CDP の `Input.dispatchMouseEvent`、`Input.dispatchKeyEvent`、`Input.insertText` を使う。設定ストレージの直接書き換えや DOM の `.click()` では、操作の検証を代用しない。
3. フィルターを1つ適用する。UI の選択値を確認し、実投稿の指標・日時・種類と表示結果を照合する。`data-sift-filter-state` と `data-sift-filter-reason` は補助情報として使う。これらの属性だけでは期待値が正しいことを証明できない。
4. フィルターを解除し、非表示状態が残らないことを確認する。
5. 追加読み込みで件数が変わった場合は、対象投稿と確認時点を記録して比較する。件数は固定とみなさない。連続読み込みが続く場合は条件を解除し、そのケースを中断したことを記録する。

除外対象の投稿がない場合は「操作確認のみ」と記録し、効果確認済みには数えない。指標が欠損した投稿は、仕様上、非表示にしない。

## 接続とアクセス権

接続とアクセス権は、毎回のスモークテストで確認する。表の85ケースとは別に実施し、通常の開閉確認では代用しない。パネルを閉じても `activeTab` の権限は残るため、準備起動後の開閉だけでは未許可状態を確認できない。

```sh
npm run smoke:connection
```

実行前に、手動確認用の開発用 Chrome を閉じる。X のプロフィールを閲覧できるよう、開発プロファイルでログインしておく。コマンドは Chrome を起動し、検証用タブを2つ作って次の状態を確認する。

| 状態 | 合格条件 |
| --- | --- |
| X のプロフィールで拡張アクションを実行する | 対象タブの最低いいね数などの操作欄が表示される |
| 同じタブで YouTube へ移動する。拡張アクションは実行しない | パネルが自動で閉じ、ページ幅が開く前に戻る |
| YouTube で拡張アクションを実行する | 同じタブに再接続し、最低再生回数などの操作欄が表示される |
| YouTube を再読み込みする | 操作欄が復旧する |
| 同じ YouTube チャンネルの配信一覧へ移動する | パネルが開いたままで、操作欄が復旧する |
| 別の X プロフィールタブで拡張アクションを実行する | 接続先が新しいタブに変わり、最低いいね数の操作欄が表示される |
| 元の YouTube タブへ戻る | 接続先と操作欄が YouTube に戻る |

各段階で、パネルの可視状態、表示寸法、アクティブタブ ID、サイト別の内容を照合する。セッションストレージのタブ ID は最後の起動先を示すため、現在の接続先の証拠には使わない。期待した状態を連続して確認できなければ失敗とする。ログイン画面、読み込み失敗、権限が常時付与された環境などで前提を再現できない場合も、合格にはしない。

結果は `test-results/connection-smoke.json` に保存される。失敗時は終了コード1になる。ビルド ID は準備時の記録と併せて残す。

終了時は作成したタブだけを閉じ、退避した設定を復元する。設定の退避先は `test-results/connection-settings-before.json`。強制終了した場合も、このデータから設定を復元し、作成したテスト用タブを閉じる。

この検証の対象は CDP 経由の接続状態である。ツールバーの実クリックに固有の問題や、全ページのフィルター動作までは検証できない。

## 対象外ページとページ遷移

以下の確認も、表の85ケースとは別に実施する。対象外ページで拡張アクションを実行し、案内パネルが開くことを確認する。フィルター操作欄が表示されず、ページ上に非表示状態が残らないことも確認する。

| サイト | 対象外の代表例 |
| --- | --- |
| YouTube | チャンネルホーム、古い順、サイト全体の検索、登録チャンネル、視聴ページ |
| ニコニコ動画 | 古い順、再生数が少ない順、コメント順など他の並び順、検索、タグ、マイリスト |
| X | おすすめ、検索の最新以外、個別投稿、プロフィールのポスト以外のタブ |
| Bluesky | カスタムフィード、検索の最新以外、個別投稿、プロフィールの返信 |
| 対象外サイト | example.com など |

対象外サイトに処理が注入されないことは、バックグラウンド処理のテストと併せて確認する。

パネルを開いたまま、対応ページから対象外ページへ移動し、対応ページへ戻る操作を確認する。並び順の変更、タブの切り替え、再読み込みも確認する。パネルを閉じて開き直したときは、選択値が「指定なし」に戻ることを確認する。拡張機能の更新を挟むケースは、ビルドごとに結果を記録する。

## 結果の記録と終了処理

結果は Git 管理外の `test-results/` に保存する。日時、ビルド ID、Chrome のバージョン、ページ、並び順、操作方法、条件、期待値、実測結果、判定、未確認の理由を記録する。記録には次の形式を使える。

| ページ・並び順 | 起動方法と結果 | フィルター | 条件 | 期待値・実測結果 | 判定・理由 |
| --- | --- | --- | --- | --- | --- |
| | CDP アクション／実クリック | | | | 合格／不合格／操作確認のみ／N/A／未実施 |

起動を確認した状態数とフィルターのケース数は、別々に集計する。途中結果や古いビルドの結果を、全件完了として扱わない。途中で修正した場合はビルド ID を更新し、影響するケースを再検証する。

終了時は変更した設定を元に戻す。一時リスナーを解除し、CDP 接続を閉じる。用済みのテスト用タブは閉じ、再利用するタブはプロファイルに残す。検証コマンドの終了処理で Chrome も閉じる。検証だけを依頼された場合は、失敗を見つけても実装を変更せず、結果を報告する。

## 配備前の検証

### 検証の実行順序

全検証は、変更箇所と既知の失敗を部分検証で解消した後、配備前の最終確認として1回実行する。

1. 報告されたページで再現する。変更箇所の単体テストと、対象ページの部分検証を先に実行する。表示形式に依存する判定では、操作欄がある場合だけでなく、正常に省略される場合、読み込み途中、未知の表示を区別する。
2. 基準の登録・更新を済ませ、差分を確認する。通常の比較で対象ケースが通ることを確認する。除外効果の代表ケースでは、実際に除外対象があることも確認する。外部サイトの見出し変更など、拡張機能と無関係な検証前提の不一致も、この段階で解消する。
3. ソース、テスト、基準、文書の変更を終えて候補をビルドする。検証中はこれらを編集せず、開発用 Chrome を使う実機検証も同時に実行しない。
4. `npm run verify:candidate` を実行する。通過後は同じ成果物を配備する。

全検証が失敗した場合は、結果を読んで、実装、検証の期待値、ログイン・通信・保存回数制限などの環境問題に切り分ける。失敗ケースを `npm run test:live -- --grep <ケース名>` で再確認し、必要な修正を終えてから全検証へ戻る。原因を確認しないまま全検証を繰り返さない。再実行前には、失敗の原因、修正または環境の復旧内容、部分検証の結果を説明する。

保存回数制限が出た場合は、設定の退避・復元と検証用タブの後片付けを確認し、開発用 Chrome の再起動などで復旧してから再確認する。制限値や判定を緩めて合格にしない。

文書や作業指示だけの変更では、Markdown の検査と差分確認を行う。拡張機能の再ビルド、実機検証、配備は、その変更だけを理由に実行しない。

### 合格の報告

途中のログやケース数だけで全検証の通過を報告しない。終了コード、`.output/verified-candidate.json` の `status` とビルド ID、実機レポート、接続確認の結果を照合する。全ケースが通っても、代表ページの除外効果が不足して合格記録が発行されていなければ、配備前の検証は未完了とする。

検証記録には実行範囲、所要時間、再実行した場合の理由を残す。部分検証、全検証、配備済みの状態を分けて報告する。

### 全検証と配備

配備に必要な全検証は `npm run verify:candidate` で実行する。一部のケースだけを実行した結果や、基準更新時の結果は、配備の合格記録には使わない。

全検証後、main の主作業ツリーで `npm run deploy:local` を実行する。このコマンドはソースと成果物のハッシュを再確認し、検証済みの成果物を配備する。詳しくは [互換性検証の設計](互換性検証の設計.md) を参照する。
